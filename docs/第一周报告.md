### 一、项目的需求描述

#### 1. 功能需求

**(1) 业务逻辑（核心交易链路）**
本系统模拟基于C/S架构的社交零售平台（微商系统），业务逻辑覆盖从“逛”到“买”再到“售后”的全流程：

- **商品展示模块**：客户端启动后向服务端发起请求（协议码`1001`），拉取商品列表（含名称、价格、库存、图片描述等）。
- **购物车管理模块**：支持将商品加入购物车（协议码`10020001`）、修改数量、删除商品。购物车数据暂存客户端内存，结算时统一提交。
- **混合促销策略模块**：支持多种促销方式的自由组合。
  - **打折**（如统一9折，第2件9折，第3件8折，甚至免单）。
  - **降价**（直降X元）。
  - **券**（满减优惠券）。
  - **混合策略**：利用策略模式（Strategy）定义算法族，利用装饰模式（Decorator）对促销进行层层叠加（例如：先执行“满200减30”，再叠加“9折券”）。
- **结算与订单模块**：提交购物车并应用促销策略（协议码`1003`），服务端计算最终金额，生成订单，扣减库存，返回结算结果（成功协议码`2003`）。
- **售后服务模块**：支持退货申请（需校验购买记录），并支持异步处理（如审核流程）。

**(2) UI描述**
- **客户端UI**：采用**控制台交互**（Windows/Linux终端），利用ASCII表格展示商品列表。
- **交互流程**：用户通过键盘输入数字选项（如“1. 查看商品”、“2. 查看购物车”、“3. 结算”、“4. 申请退货”）。
- **风格可选（课件要求）**：体现柔性设计，程序启动时允许用户选择“极简风格（只显示文字）”或“详细风格（带边框和分隔符）”，通过**策略模式**动态切换UI渲染算法。

**(3) 通信**
- **物理层**：基于`Winsock`（Windows）或`Berkeley Socket`实现**TCP面向连接**的可靠传输。
- **协议层（课件示例）**：自定义**应用层协议**，采用**定长头部+变长体部**。
  - **请求格式**：`[协议码(4字节)] [数据长度(4字节)] [JSON/字符串数据]`。
  - **核心交互**：
    - `1001`（请求商品列表） -> 响应 `2001`（返回商品JSON数组）。
    - `1002`（加入购物车，携带商品ID和数量） -> 响应 `2002`（加入成功/库存不足）。
    - `1003`（提交结算，携带购物车所有项） -> 响应 `2003`（返回订单总价和明细）。
  - **双向通信**：客户端发起请求，服务端必须返回应答（同步阻塞模式），但服务端内部处理请求时采用异步队列（见下文性能需求）。

---

#### 2. 性能需求

**(1) 多层结构（对应课件MVC架构）**
严格落地**四层物理/逻辑架构**，确保高内聚低耦合：

| 层级 | 对应模块 | 核心职责（C++实现） |
| :--- | :--- | :--- |
| **客户端表示层 (Client UI)** | `client/ui/` | 捕获键盘输入、渲染菜单和数据表格。**禁止**包含任何业务判断（如计算折扣）。 |
| **服务端业务层 (Server BLL)** | `server/service/` | 实现促销策略算法、库存扣减逻辑、订单生成。接收DTO（数据传输对象），返回VO（视图对象）。 |
| **服务端持久层 (Server DAL)** | `server/repository/` | 负责将`Product`、`Order`等对象**映射**（ORM思想）到数据库表，执行增删改查SQL。 |
| **数据库层 (DB)** | `SQLite`或`MySQL` | 存储用户表、商品表、订单表、库存表。 |

**(2) 柔性讨论**
- **UI柔性**：利用**抽象工厂模式**，可一键切换“控制台UI”和“未来可能的Qt/图形UI”，业务层代码零改动。
- **促销柔性**：新增促销活动（如“买一送一”）时，只需新增一个继承自`PromotionStrategy`的子类，无需修改结算核心逻辑（**开闭原则**）。
- **异常柔性**：网络断连时，客户端自动重试3次；数据库连接失败时，服务端降级返回“系统维护中”错误码，严禁闪退。

**(3) 扩展能力**
- **并发处理（双9.9大促场景）**：服务端采用**线程池 + 消息队列**处理请求。客户端请求先入队，工作线程异步取出处理（**观察者模式**触发交易完成事件）。
- **互斥处理（爱马仕限量场景）**：对库存扣减操作使用`std::mutex`（互斥锁）行锁，确保超卖现象绝不发生（如库存为1时，两个并发请求只有一个能成功）。
- **跨语言扩展**：协议使用纯文本JSON和固定二进制头，若未来服务端改用Java，客户端C++代码**无需任何修改**，仅靠Socket通信即可互通。

### 三、关于设计的初步思考

基于课件强调的“C/S + MVC”，我初步构思了**服务端**和**客户端**的静态结构及动态协作。

**1. 服务端核心类图设计（UML简稿）**

- **实体层（Model）**：
  - `Product`（商品ID，名称，价格，库存）。
  - `Order`（订单ID，用户ID，总金额，状态）。
  - `User`（用户ID，密码，等级）。
- **业务层（Service）**：
  - `ICommandHandler`（**抽象接口**）：负责解析协议码，所有Handler都实现`execute(jsonReq, jsonRes)`。
  - `ShowProductHandler`（处理1001）、`AddCartHandler`（处理1002）、`CheckoutHandler`（处理1003）。
  - `PromotionContext`（策略上下文）：持有当前选中的`IPromotion`链表，结算时遍历链表应用所有促销。
- **异步层（Observer）**：
  - `TaskQueue`（单例）：负责维护请求队列。`WorkerPool`（观察者）监听队列，有新任务时唤醒并处理，处理完后通过`notifyClient()`异步应答。

**2. 客户端核心类图设计**

- `TcpClient`：封装`connect`、`sendRequest`、`receiveResponse`。
- `LocalCart`：存储用户临时添加的商品（`map<int, int>` 商品ID->数量）。
- `UIRenderer`（抽象基类）：提供`drawHeader()`、`drawProductTable()`，派生类`SimpleRenderer`和`FancyRenderer`实现不同风格。

**3. 关键业务流程时序（重点——结算）**

1. 客户端`UI`获取用户确认 -> 2. 客户端`LocalCart`组装结算请求JSON -> 3. 客户端`TcpClient`发送协议码`1003` -> 4. 服务端`TaskQueue`入队（异步） -> 5. 服务端`Worker`取出任务，调用`CheckoutHandler` -> 6. `CheckoutHandler`从数据库`ProductRepository`锁定库存 -> 7. 遍历`PromotionChain`计算最终价格（策略+装饰） -> 8. 生成`Order`对象，调用`OrderRepository`存入数据库 -> 9. 打包`2003`应答回传客户端 -> 10. 客户端展示“支付成功”。

### 四、你准备做到什么难度，为什么？

**我准备达到的难度等级：高标准“三个难点+” & 满足全部要求**

结合课件的考核标准（功能极简无扩展扣分，三个以上难点加分），我的难度规划如下：

**1. 必达的“三个以上难点+”：**
- **难点一（通信层）**：实现**自定义TCP应用层协议**，解决粘包/拆包问题，并实现请求超时重传机制（非阻塞`select`监测）。
- **难点二（并发层）**：在服务端完美落地**生产者-消费者异步线程池模型（观察者模式）**，模拟高并发下双9.9场景，并用互斥锁解决库存超卖（限量爱马仕场景）。
- **难点三（设计模式层）**：不仅实现策略+装饰的**混合促销链**（如先满减再打折），还额外引入**职责链模式**处理售后审核流程（不同金额的退货走不同级别审核）。
- **难点四（持久层）**：手写一个极简的**ORM映射工具类**，通过C++模板元编程，实现实体类与SQLite表的自动双向映射（虽然简陋，但体现架构思想）。
