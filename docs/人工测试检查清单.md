# 微商系统 — 人工测试检查清单

> 与自动化测试（test_client.exe，79 项断言）互补，以下 7 项需手动操作客户端确认。
> 所有步骤基于实际 C++ 实现，菜单编号与 `client/Renderers.h`、`client/ClientController.cpp` 一致。

---

## 前置准备（每次测试前必做）

1. **启动服务端**：双击 `build\server.exe`（或命令行运行），看到"微商系统服务端已启动，监听端口 8888"。
   - 首次启动自动创建 `ms.db` 并初始化 3 用户 / 6 商品 / 6 促销。
2. **启动客户端**：另开一个终端，运行 `build\client.exe`。
3. **测试账号**：`admin / Admin#2026!`，`user1 / User1#2026!`，`user2 / User2#2026!`。

| 用户名 | 等级 | 用途 |
|--------|------|------|
| `admin` | VIP（level=2，管理员） | 审核退货、VIP 折上折验证 |
| `user1` | 普通（level=1） | 普通用户下单、退货、越权测试 |
| `user2` | 普通（level=1） | 备用 |

> 如需重置数据库：关闭服务端，删除 `ms.db`，重新启动服务端即可重新初始化。

## 检查项 1：客户端中文显示正常

**操作步骤**：
1. 启动客户端，首屏显示 `===== 微商系统 v1.0 =====`（或详细风格的 ASCII 欢迎框）。
2. 选择 UI 风格（输入 `1`/`2`/`3`），看到"正在连接服务端 127.0.0.1:8888 ..."、"连接成功"、"心跳正常，服务端在线"。
3. 登录界面显示 `1. 登录  2. 注册  0. 退出`。
4. 登录 `user1`，主菜单显示中文菜单项（查看商品、购物车、结算、我的订单、申请退货、切换UI皮肤、销售统计、搜索商品、联系客服、退货进度、退货审核(管理员)、退出）。
5. 主菜单选 `1` 查看商品，表格中"名称""价格""库存""分类"表头及商品名（高端护肤品套装、有机茶叶礼盒等）均为中文。

**预期结果**：
- 全程无乱码（无 `???` 或方块字符）。
- 中文对齐基本整齐（`displayWidth` 按 UTF-8 中文字符占 2 列计算对齐）。
- 错误提示如"[错误] 库存不足"也为中文。

**判定标准**：所有界面文字、商品名、提示信息均正常显示中文，无乱码、无缺字。

## 检查项 2：三套主题切换正常

**操作步骤**：
1. 客户端启动时，首屏提示"选择 UI 风格：1. 极简×蓝 2. 详细×绿 3. 详细×粉"。
2. 输入 `1`，确认提示"已切换到蓝色-极简风格"，观察界面文字为**蓝色**系（标题亮蓝、提示蓝色），且无 ASCII 边框（纯文字列表）。
3. 登录后，主菜单选 `6`（切换UI皮肤），输入 `2`，提示"已切换到绿色-详细风格"，观察界面变为**绿色**系且出现 ASCII 边框（`+----+` 表格框）。
4. 再次选 `6`，输入 `3`，提示"已切换到粉色-详细风格"，界面变为**粉色**系，仍保留 ASCII 边框。
5. 每次切换后，选 `1` 查看商品，确认商品表格的边框/表头颜色随主题变化。

**三套皮肤对应关系**（依据 `ClientController::createSkin`）：

| 编号 | 主题色 | UI 风格 | 具体工厂 |
|------|--------|---------|----------|
| 1 | 蓝色 | 极简（无框） | BlueThemeFactory.createSimple() |
| 2 | 绿色 | 详细（ASCII 框） | GreenThemeFactory.createFancy() |
| 3 | 粉色 | 详细（ASCII 框） | PinkThemeFactory.createFancy() |

**预期结果**：
- 切换后立即生效，无需重启。
- 颜色明显区分（蓝/绿/粉），极简与详细风格的边框差异可见。
- 切换后商品列表、购物车、订单等所有界面统一使用新主题。

**判定标准**：三套皮肤均可切换，颜色与风格符合上表，切换后全界面一致。

## 检查项 3：商品价格显示正确

**操作步骤**：
1. 登录任意账号，主菜单选 `1` 查看商品。
2. 对照下表核对价格列（服务端以整数分存储，客户端 `/100.0` 转元，保留 2 位小数）：

| ID | 商品名 | 数据库存储（分） | 客户端应显示（元） | 库存 |
|----|--------|------------------|-------------------|------|
| 1 | 高端护肤品套装 | 29900 | 299.00 | 15 |
| 2 | 有机茶叶礼盒 | 18800 | 188.00 | 32 |
| 3 | 手工皮具钱包 | 39900 | 399.00 | 8 |
| 4 | 降噪无线耳机 | 89900 | 899.00 | 5 |
| 5 | 智能手环 | 24900 | 249.00 | 20 |
| 6 | 限量款背包 | 129900 | 1299.00 | 1 |

3. 输入商品 ID（如 `1`）查看详情，详情行价格也应为 `299.00`。
4. 选 `1` 将商品 1 加入购物车，数量 `2`；主菜单选 `2` 查看购物车，小计应为 `598.00`（299.00 × 2），合计 `598.00`。

**预期结果**：
- 价格均为 2 位小数，无浮点异常（如 298.999999）。
- 购物车小计 = 单价 × 数量，合计 = 各小计之和。
- 价格与 `database/init_data.sql` 中的种子数据一致。

**判定标准**：6 个商品价格全部对上表，购物车小计/合计计算正确，无浮点误差。

## 检查项 4：订单状态和退货状态显示正确

> 本项需完整走一遍"下单 → 申请退货 → 管理员审核"流程，观察状态流转。

### 4.1 下单后订单状态

1. 登录 `user1`，将商品 1 加入购物车（数量 2）。
2. 主菜单选 `3` 结算，促销选 `2`（满200减30），确认下单。
3. 主菜单选 `4` 我的订单，看到刚生成的订单。

**预期**：订单状态显示 **"已支付"**，无退货标记（return_status=0 不显示标记）。实付显示 `568.00`（598 - 30）。

### 4.2 申请退货后状态

1. 记下订单号（订单#N），主菜单选 `5` 申请退货。
2. 输入该订单 ID，退货原因输入"质量问题"。
3. 提示"退货申请已提交，等待审核"。
4. 主菜单选 `4` 我的订单，再次查看该订单。

**预期**：
- 订单状态变为 **"退货中"**。
- 订单行末尾出现 **"[退货待审核]"** 标记。
- 主菜单选 `10` 退货进度，可看到该退货单，状态为"待审核"。

### 4.3 管理员审核通过后状态

1. 退出客户端（选 `0`），重新启动，登录 `admin`。
2. 主菜单选 `11` 退货审核，看到待审核退货单列表。
3. 输入退货 ID，选 `1`（通过，回补库存）。
4. 提示"已通过，库存已回补"。
5. 退出，重新登录 `user1`，主菜单选 `4` 我的订单。

**预期**：
- 该订单状态变为 **"已取消"**。
- 退货标记变为 **"[退货已通过]"**。
- 商品 1 的库存从 13 恢复为 15（退货回补了 2 件）——可通过选 `1` 查看商品确认库存。

### 4.4（可选）审核拒绝分支

如需验证拒绝分支：另下一单 → 申请退货 → admin 审核选 `2`（拒绝）→ user1 查看订单，状态恢复为"已支付"，标记为"[退货已拒绝]"。

**状态码对照**（依据 `Renderers.h`）：

| 订单 status | 显示 | 退货 return_status | 显示标记 |
|-------------|------|-------------------|----------|
| 0 | 待支付 | 0 | （无标记） |
| 1 | 已支付 | 1 | [退货待审核] |
| 2 | 已发货 | 2 | [退货已通过] |
| 3 | 已完成 | 3 | [退货已拒绝] |
| 4 | 已取消 | | |
| 5 | 退货中 | | |

**判定标准**：下单→退货中→已取消/已支付 的状态流转与标记完全符合上表，库存回补正确。

## 检查项 5：普通用户不能审核退货

**操作步骤**：
1. 登录 `user1`（普通用户）。
2. 先按检查项 4.1–4.2 下一笔订单并申请退货（确保存在待审核退货单）。
3. 主菜单选 `11` 退货审核(管理员)。
4. 客户端会先拉取退货列表（user1 只能看到自己的退货单），输入该退货 ID。
5. 选 `1`（通过）。

**预期结果**：
- 服务端返回 **4002（未登录/无权限）**，客户端显示错误提示（如"请先登录"或"无权限"）。
- 退货单状态**不变**（仍为"待审核"）。
- 换 `admin` 登录查看，该退货单仍在待审核列表中。

**原理**：`ReturnAuditHandler` 调用 `Auth::requireAdmin`，校验 token 绑定用户的 `level >= 2`；普通用户 level=1，校验失败返回 `ErrorCodes::UNAUTHORIZED(1011)`，协议码升级为 4002。

**判定标准**：普通用户执行审核被拒绝，退货单状态未被改变，无库存变动。

## 检查项 6：未登录用户不能访问业务接口

> 客户端 GUI 在 `run()` 中强制 `loginLoop()` 成功后才进入 `mainLoop()`，因此正常操作无法绕过登录。
> 本项需通过**原始 TCP 请求**验证服务端鉴权，确认即使绕过客户端也无法访问。

### 方法 A：用 PowerShell 发送原始报文（推荐）

1. 确保服务端已启动。
2. 打开 PowerShell，进入项目目录，执行以下脚本（发送一个不带 token 的 1040 订单查询请求）：

```powershell
$client = New-Object System.Net.Sockets.TcpClient("127.0.0.1", 8888)
$stream = $client.GetStream()
# 构造请求体：不带 token 的订单查询
$body = [System.Text.Encoding]::UTF8.GetBytes('{"user_id":1}')
# 16 字节头（大端）: Magic="MI_S"  Version=1  Code=1040  Length=body长度
$magic = [byte[]]@(0x4D,0x49,0x5F,0x53)
$ver   = [byte[]]@(0,0,0,1)
$code  = [BitConverter]::GetBytes([uint32]1040); [Array]::Reverse($code)
$len   = [BitConverter]::GetBytes([uint32]$body.Length); [Array]::Reverse($len)
$packet = $magic + $ver + $code + $len + $body
$stream.Write($packet, 0, $packet.Length)
Start-Sleep -Milliseconds 300
# 读 16 字节响应头
$respHead = New-Object byte[] 16
$stream.Read($respHead, 0, 16) | Out-Null
# 大端转小端读取协议码（字节 8-11）和体长度（字节 12-15）
$rc = $respHead[8..11]; [Array]::Reverse($rc)
$rl = $respHead[12..15]; [Array]::Reverse($rl)
$respCode = [BitConverter]::ToUInt32($rc, 0)
$respLen  = [BitConverter]::ToUInt32($rl, 0)
$respBody = New-Object byte[] $respLen
if ($respLen -gt 0) { $stream.Read($respBody, 0, $respLen) | Out-Null }
Write-Output ("响应协议码: " + $respCode)
Write-Output ("响应体: " + [System.Text.Encoding]::UTF8.GetString($respBody))
$client.Close()
```

**预期输出**：
```
响应协议码: 4002
响应体: {"err_code":1011,"err_msg":"请先登录"}
```

### 方法 B：观察客户端强制登录

1. 启动客户端，在登录界面选 `0` 退出——程序直接结束，不会进入主菜单。
2. 不存在任何不登录就能操作业务的入口。

**判定标准**：不带有效 token 的业务请求（1040 等）返回 4002，客户端无法绕过登录进入业务菜单。

## 检查项 7：购物车为空时不能结算

**操作步骤**：
1. 登录任意账号（如 `user1`）。
2. 主菜单选 `2` 购物车，确认显示"购物车为空"（如之前加过商品，选 `3` 清空）。
3. 返回主菜单，直接选 `3` 结算。

**预期结果**：
- 客户端**不发送任何网络请求**，直接显示红色错误提示：`[错误] 购物车为空，请先添加商品`。
- 停留在主菜单，不进入促销选择界面。

**原理**：`ClientController::handleCheckout()` 首行判断 `if (cart_.isEmpty())`，直接 return，不调用 `sendAndRecv`。

**对比验证**（可选）：
1. 选 `1` 查看商品，加入任意商品到购物车。
2. 再选 `3` 结算，此时正常进入促销选择界面，可完成下单。

**判定标准**：空购物车时结算被客户端本地拦截，提示明确，不产生无效请求；有商品时结算流程正常。
