## 第二周课程设计报告


### 一、项目的需求的进一步理解和描述

#### 1.1 对项目本质的再认识

经过第一周的需求梳理和第二周的深入思考，我对本项目有了更清晰的认识。课件明确指出，微商系统的**本质是“社交+零售”** ，其核心业务模式是“引流+吸粉+交易”。这意味着本系统不仅仅是传统的电商平台，而是需要模拟社交零售环境下的交易闭环——用户通过客户端浏览商品、加入购物车、享受促销优惠、完成结算，并支持售后服务。

从功能定位来看，本系统对标的是“手机淘宝、京东”等移动电商平台，但课件明确约定 **“PC下实现即可，不考虑手机”** 。因此，我们的实现将立足于Windows/Linux PC环境，采用控制台交互方式完成全部功能演示。

#### 1.2 架构选型的进一步理解

课件给出了两种架构选型方案：

- **C/S框架**：服务器和客户端都要安装程序，采用MVC模式，通过TCP/IP通信。
- **B/S框架**：服务器端程序+浏览器，通过HTTP通信，服务端部署在Web容器中。

**本项目选择C/S框架**。理由如下：课件明确要求实现“自定义TCP/IP协议通信”，这是C/S架构的典型特征；同时，C/S架构能够更充分地展示面向对象程序设计的核心能力——包括多线程、网络编程、设计模式应用等，与本课程“C++面向对象程序设计”的教学目标高度吻合。

#### 1.3 功能需求的细化

基于课件中的功能描述，我将系统功能进一步细化为六个核心模块：

| 模块 | 子功能 | 说明 |
|------|--------|------|
| **商品展示** | 查看产品列表 | 客户端发起1001请求，服务端返回商品信息 |
| **购物车管理** | 加入/删除/修改 | 协议码10020001表示加入购物车操作 |
| **促销策略** | 混合促销 | 采用反射+策略+装饰等模式实现打折、降价、券等 |
| **结算** | 订单生成与支付 | 协议码1003发起结算，服务端计算并返回结果 |
| **售后服务** | 退货申请与处理 | 支持购买记录校验和异步审核流程 |
| **UI风格切换** | 不同风格UI选择 | 体现系统的柔性设计能力 |

#### 1.4 性能需求的深化理解

课件从三个维度提出了性能要求：

**（1）并发处理**——“考虑并发，如双9.9”。这要求服务端能够同时处理多个客户端的请求。在C/S架构下，我们需要设计线程池或异步IO机制来应对并发场景。

**（2）互斥机制**——“考虑互斥，如爱马仕限量，Costco”。这要求对共享资源（如库存）的访问必须线程安全。当多个用户同时抢购同一限量商品时，必须通过互斥锁保证库存扣减的正确性，避免超卖。

**（3）同步/异步通信**——课件要求“同步或者异步通信”。同步通信适用于需要即时确认的操作（如加入购物车），而异步通信更适合耗时操作（如订单处理、售后审核），可以通过消息队列实现请求的缓冲和异步处理。

#### 1.5 “柔性”的内涵

课件多次强调“分层设计体现柔性”。所谓柔性，我理解为系统对变化的适应能力：
- **业务柔性**：促销策略可以灵活组合和扩展，新增一种促销方式无需修改核心结算逻辑。
- **UI柔性**：用户可以切换不同风格的界面，UI渲染算法可动态替换。
- **部署柔性**：分层架构使得替换某一层实现（如从文件存储切换为数据库）不影响其他层。


### 二、讨论可能的相关技术

#### （1）C/S结构和B/S结构

**C/S结构（Client/Server，客户端/服务器）** 是指将应用程序分为客户端和服务器端两部分，客户端负责用户交互和部分业务逻辑，服务器端负责数据管理和核心业务处理。客户端需要单独安装，通过网络与服务器通信。

**B/S结构（Browser/Server，浏览器/服务器）** 是C/S结构的演变，用户只需通过浏览器访问，无需安装客户端软件。绝大部分工作由服务器承担。

| 对比维度 | C/S结构 | B/S结构 |
|----------|---------|---------|
| 客户端 | 需安装专用软件 | 只需浏览器 |
| 维护升级 | 每台客户端需更新 | 只需更新服务器 |
| 交互体验 | 丰富、响应快 | 受浏览器限制 |
| 跨平台 | 需为不同OS开发不同版本 | 一次开发多端适配 |
| 安全性 | 较高，可自主控制 | 需额外设计 |

本项目选择C/S结构，因为课件明确要求TCP/IP自定义协议通信和客户端程序开发，C/S架构能更好地体现网络编程和面向对象设计能力。

#### （2）MVC框架

MVC（Model-View-Controller）是一种**设计模式**，其目的是将业务逻辑和界面展示分开。MVC由三部分组成：

- **Model（模型）** ：封装数据与业务逻辑
- **View（视图）** ：负责数据展示和用户交互
- **Controller（控制器）** ：接收用户输入，调用Model处理，选择View展示

**MVC与三层架构的区别**：三层架构（表现层-业务层-持久层）是一种**软件架构**，而MVC是一种**设计模式**。两者的目标一致——都是为了解耦和提高代码复用。三层架构更关注系统层面的横向分层，MVC更关注表示层内部的职责分离。

在本项目中，客户端采用MVC模式：UI层作为View，业务逻辑处理作为Controller，数据模型作为Model；服务端采用三层架构：表现层（处理协议）、业务层（促销、结算）、持久层（数据库操作）。

值得一提的是，MVC的威力离不开**组合模式、策略模式、观察者模式**的默契配合——这正好与课件要求的设计模式应用相呼应。

#### （3）持久层

**持久层（Persistence Layer）** 是专注于实现数据持久化的逻辑层面，将数据使用者和数据实体相关联。**持久化**的本质是将内存中的数据保存到磁盘等永久存储介质中。

**ORM（对象关系映射，Object Relational Mapping）** 是持久层的一种实现模式。ORM的核心思想是：应用程序不再直接访问数据库，而是以面向对象的方式操作持久化对象，ORM框架将这些操作转化为底层的SQL操作。通过ORM，可以把对象映射到关系型数据库中。

在本项目中，我们将实现一个轻量级的ORM层：
- `Product`、`Order`、`User`等实体类映射到数据库表
- 通过模板函数实现对象的`INSERT`、`SELECT`、`UPDATE`操作
- 使用SQLite作为嵌入式数据库，无需额外安装

#### （4）设计模式

课件明确要求使用**反射+策略+装饰等模式**实现混合促销策略。结合项目需求，我计划应用以下设计模式：

**策略模式（Strategy Pattern）** ：定义一系列算法族，使它们可以互相替换。在本项目中，`DiscountStrategy`（打折）、`PriceCutStrategy`（降价）、`CouponStrategy`（券）都实现统一的`IPromotion`接口，结算时动态选择。

**装饰模式（Decorator Pattern）** ：动态地给对象添加额外的职责。在本项目中，促销可以层层叠加——先执行满减，再执行打折，再使用优惠券——每个装饰器包装前一个促销对象。

**观察者模式（Observer Pattern）** ：定义对象间的一对多依赖关系。在本项目中，服务端的消息队列消费者（Worker）作为观察者，监听新请求的到来；订单状态变更时通知相关模块。

**工厂模式（Factory Pattern）** ：用于创建促销策略对象，根据配置动态生成对应的策略实例。

#### （5）Web服务

**Web Service（Web服务）** 是一种跨平台、跨语言的网络服务，遵循特定标准（如SOAP协议），通过HTTP/HTTPS调用。Web服务具有以下特性：
- 通过Web访问
- 通过标准互联网协议传输XML消息
- 平台独立、低耦合、自包含
- 可用于开发分布式的互操作应用程序

**Web Service与微服务**：微服务架构致力于松耦合和高内聚，常通过RESTful API和轻量级消息通信协议完成；而传统SOA以ESB为核心，基于Web Service标准实现。

在本项目中，虽然我们不直接实现Web Service，但课件提到的“Web服务”概念体现在：服务端作为独立的服务进程，通过TCP/IP协议为多个客户端提供服务——这本质上是一种面向服务的架构思想。课件还提到“可以服务器Java、客户端C++跨语言”，这正是Web服务“跨语言互操作”精神的体现。

#### （6）并发和互斥

**并发（Concurrency）** 是指多个任务在同一时间段内交替执行。在多线程环境下，多个线程可能同时访问共享资源，这就引出了**线程安全**的问题。

**互斥（Mutex）** 是保证线程安全的重要手段。通过互斥锁，确保同一时刻只有一个线程能够访问临界区（共享资源）。

**本项目中的并发与互斥场景**：
- **并发**：服务端使用线程池同时处理多个客户端的请求，模拟“双9.9”高并发场景
- **互斥**：库存扣减操作必须加锁，防止“爱马仕限量”超卖问题——当库存为1时，两个并发请求只有一个能成功

#### （7）JavaEE、JSP、JavaScript

课件在延伸思考中提到了Web编程相关技术，理解这些概念有助于拓宽技术视野：

**JavaEE（Java Platform, Enterprise Edition）** ：Java的企业级开发平台，提供了一整套用于开发企业级应用的技术规范，包括Servlet、JSP、EJB等。

**JSP（JavaServer Pages）** ：JavaEE中的一部分，是一种用于生成动态网页的服务端技术。JSP在服务器端执行，生成HTML页面后发送给浏览器。

**JavaScript**：一种运行在浏览器端的客户端脚本语言，用于实现网页的动态效果和用户交互。**JavaScript与Java没有直接关系**，两者是独立的技术。

课件之所以提及这些技术，是因为“Web编程”是B/S架构的核心技术栈。虽然本项目采用C/S架构、使用C++实现，但理解这些概念有助于我们更好地理解B/S架构的工作原理，也为未来可能的架构演进（如增加Web管理后台）预留知识储备。

#### （8）同步和异步通信

**同步通信（Synchronous Communication）** 是一种请求-响应模式：客户端发送请求后会**阻塞**，直到服务端返回响应。同步通信简单直观，适合需要即时确认的场景，如金融交易、在线支付等。

**异步通信（Asynchronous Communication）** 不要求即时响应：客户端发送请求后**不需要等待**服务端的回复即可继续执行其他操作。异步通信通常通过消息队列等中间件实现，适用于复杂、高并发的系统，能实现服务解耦、性能提升和流量削峰。

| 对比维度 | 同步通信 | 异步通信 |
|----------|----------|----------|
| 响应方式 | 请求后阻塞等待 | 请求后立即返回 |
| 复杂度 | 较低 | 较高 |
| 适用场景 | 强一致性、低延迟 | 高并发、松耦合 |
| 资源效率 | 线程可能长时间等待 | 线程可继续处理其他任务 |

**在本项目中的设计**：
- **同步通信**：商品展示、加入购物车等需要即时反馈的操作
- **异步通信**：结算处理、售后审核等耗时操作——客户端提交结算请求后立即收到“处理中”的应答，服务端通过消息队列异步处理，完成后通过观察者模式通知客户端

#### （4）数据库设计

使用**SQLite**作为嵌入式数据库，设计三张核心表：

**商品表（products）** ：
```sql
CREATE TABLE products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    price REAL NOT NULL,
    stock INTEGER NOT NULL,
    description TEXT,
    category TEXT
);
```

**用户表（users）** ：
```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT UNIQUE NOT NULL,
    password TEXT NOT NULL,
    level INTEGER DEFAULT 1,   -- 1:普通 2:VIP
    register_date DATETIME
);
```

**订单表（orders）** ：
```sql
CREATE TABLE orders (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    total_amount REAL NOT NULL,
    discount_amount REAL DEFAULT 0,
    final_amount REAL NOT NULL,
    status INTEGER DEFAULT 0,   -- 0:待处理 1:已支付 2:已发货 3:已完成
    create_time DATETIME,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

**订单明细表（order_items）** ——记录订单快照，即使商品信息后续修改也不影响历史订单：
```sql
CREATE TABLE order_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id INTEGER NOT NULL,
    product_id INTEGER NOT NULL,
    product_name TEXT NOT NULL,   -- 快照
    price REAL NOT NULL,           -- 快照
    quantity INTEGER NOT NULL,
    FOREIGN KEY (order_id) REFERENCES orders(id)
);
```

**ORM映射策略**：
- 每个实体类（`Product`、`Order`、`User`）提供`toSQL()`方法生成INSERT/UPDATE语句
- 提供模板函数`loadFromDB<T>()`从查询结果构造对象
- 继承关系的映射（如不同用户类型）通过`user_level`字段区分，不在表中体现继承关系

#### （5）通信协议设计

课件给出了协议设计示例，我们在此基础上完善：

**协议格式**：定长头部（8字节）+ 变长体部
```
+----------+----------+----------+
| 协议码(4) | 长度(4)  | 数据体   |
+----------+----------+----------+
```

**协议码定义**：

| 类别 | 协议码 | 含义 | 方向 |
|------|--------|------|------|
| 请求 | 1001 | 请求商品列表 | 客户端→服务端 |
| 响应 | 2001 | 返回商品列表 | 服务端→客户端 |
| 请求 | 1002 | 加入购物车 | 客户端→服务端 |
| 响应 | 2002 | 加入购物车结果 | 服务端→客户端 |
| 请求 | 1003 | 结算 | 客户端→服务端 |
| 响应 | 2003 | 结算结果 | 服务端→客户端 |
| 请求 | 1004 | 申请退货 | 客户端→服务端 |
| 响应 | 2004 | 退货申请结果 | 服务端→客户端 |
| 请求 | 1005 | 查询订单 | 客户端→服务端 |
| 响应 | 2005 | 返回订单信息 | 服务端→客户端 |
| 请求 | 1099 | 心跳/保活 | 客户端→服务端 |
| 响应 | 2099 | 心跳应答 | 服务端→客户端 |

**数据体格式**：采用JSON格式（轻量、可读、跨语言）
```json
// 1001请求（无数据体）
{}

// 2001响应
{
    "products": [
        {"id": 1001, "name": "高端护肤品套装", "price": 299.00, "stock": 15},
        {"id": 1002, "name": "有机茶叶礼盒", "price": 188.00, "stock": 32}
    ]
}

// 1003结算请求
{
    "user_id": 1,
    "cart_items": [
        {"product_id": 1001, "quantity": 2},
        {"product_id": 1002, "quantity": 1}
    ],
    "promotions": ["discount_0.9", "coupon_20"]  // 选择的促销策略
}

// 2003结算响应
{
    "order_id": 2026001,
    "total": 786.00,
    "discount": 98.60,
    "final": 687.40,
    "status": "success"
}
```

**粘包处理策略**：先读4字节长度，再根据长度读满指定字节数的Body（长度前缀法）。

### 四、其他你想说的

#### 4.1 关于技术学习的思考

本次课程设计涉及的技术栈超出了课堂讲授范围——TCP/IP网络编程、SQLite数据库、多线程并发等，在C++标准课程中通常只是简单提及。课件也坦诚地指出这些是“涉及新技术”。但正如课件所说，课程设计的价值不仅在于巩固已有知识，更在于**培养自主学习能力和解决实际问题的能力**。

我的学习策略是：
1. **先框架后细节**：先理解整体架构和各层职责，再深入每一层的具体实现
2. **借鉴成熟方案**：参考开源项目的设计思路（如Muduo网络库的事件驱动模型），但不盲目照搬
3. **小步迭代**：先实现单机版核心逻辑，再逐步加入网络、数据库、并发等特性
4. **文档驱动**：先写设计文档（本周报告），再编码实现

#### 4.2 关于C++实现难点的思考

**难点一：智能指针与资源管理**。服务端涉及大量的对象创建和传递（如Handler、Promotion对象），使用裸指针容易导致内存泄漏或悬空指针。计划全面采用`std::shared_ptr`和`std::unique_ptr`管理资源生命周期。

**难点二：线程安全的数据结构**。`TaskQueue`作为生产者-消费者共享队列，需要保证线程安全。计划使用`std::mutex`配合`std::condition_variable`实现阻塞队列。

**难点三：协议的可扩展性**。协议头中预留版本号和扩展字段，未来增加新协议码时无需修改解析逻辑。

#### 4.3 关于课程设计的意义

课件提到“不分组”、“个人进步巨大”作为考核维度。我认为课程设计的真正价值在于：

- **从"会写代码"到"会设计系统"** ：单机增删改查人人都会，但C/S架构、分层设计、设计模式应用才是拉开差距的地方
- **从"被动接受"到"主动探索"** ：网络编程、数据库这些课堂没细讲的内容，正是锻炼自学能力的最佳机会
- **从"面向过程"到"面向对象"** ：将设计模式落地到具体业务场景，才能真正理解多态、继承、封装的威力

我相信，通过本次课程设计，我不仅能完成一个功能完整的微商系统，更能在**系统架构能力、设计模式应用、C++现代特性**三个维度上实现“个人进步巨大”。
