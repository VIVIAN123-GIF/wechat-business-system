**推翻或修正的设计（编码过程中调整）：**

| 原设计 | 实现中遇到的问题 | 修正方案 |
|--------|-----------------|----------|
| **每客户端一个独立线程** | 客户端数量增加时，线程数膨胀，上下文切换开销大；且某个客户端socket异常会导致整条线程退出 | 改为**主线程accept + 每个客户端一个Handler对象放入线程池队列**，由固定大小的线程池处理所有客户端的请求。客户端连接本身只负责收发，业务处理由Worker线程池完成。 |
| **客户端接收线程轮询消息队列** | 接收线程每1秒超时唤醒一次，虽然功能正确但CPU空转明显 | 保持双线程模型，但将`recv`超时调整为**不超时阻塞**，仅在连接断开或收到完整包时才返回。主线程通过消息队列异步获取推送，事件驱动更自然。 |
| **订单明细作为Order的内部vector** | 从数据库加载订单时，需要额外查询`order_items`表，增加了Repository的复杂度 | 保持`Order`持有`vector<OrderItem>`的设计不变，但在`OrderRepository::findById`中执行**两次查询**（一次查主表，一次查明细），组装后返回完整对象。代价是性能略降，但语义清晰。 |
| **简约和详细两种UI风格** | 控制台字符画在不同终端（Windows CMD / PowerShell / VS Code终端）显示效果不一致 | 放弃复杂的Unicode边框字符（`╔═╗`），改用**ASCII字符**（`+---+`），兼容所有终端。同时两种风格的核心逻辑保留，仅渲染字符不同。 |

#### （2）MVC模式的体验如何？坚持分层了吗？

**整体评价**：MVC（Model-View-Controller）分层架构在本项目中得到了严格贯彻，带来的好处在编码和调试过程中体现得尤为明显。

**客户端MVC实践：**

| 层级 | 对应类/模块 | 职责 | 是否遵守 |
|------|------------|------|----------|
| **View（视图层）** | `UIRenderer`及其子类 `SimpleRenderer`、`FancyRenderer` | 纯输出：打印菜单、表格、提示信息。**绝不**包含业务逻辑。 | ✅ |
| **Controller（控制层）** | `ClientController` | 接收用户输入、调用通信层发送请求、根据响应更新Model、触发View刷新。 | ✅ |
| **Model（模型层）** | `LocalCart`、`Product`、`OrderSnapshot` | 数据持有和简单的自身操作（如`CartItem::getSubtotal()`）。不涉及网络和UI。 | ✅ |

**服务端隐式MVC（实为三层架构）：**

| 层级 | 对应模块 | 职责 | 是否遵守 |
|------|----------|------|----------|
| **业务层（Service）** | `*Handler`（如`CheckoutHandler`） | 实现具体业务规则（促销计算、库存校验、订单生成）。 | ✅ |
| **持久层（Repository）** | `ProductRepository`、`OrderRepository` | 封装所有SQL操作，上层完全不感知SQL语句。 | ✅ |
| **数据层（Model）** | `Product`、`Order`、`User` | 纯数据载体，仅有getter/setter和简单转换。 | ✅ |

**分层带来的实际好处**：
- **独立调试**：先写Repository单元测试验证数据库操作正确，再写Handler业务逻辑。分层使问题定位范围缩小。
- **替换方便**：UI风格切换只需换`renderer`指针，业务层无感。
- **代码可读性**：新人看代码能快速定位“业务规则在哪里改”——在Handler层，而非散落在UI或数据库层。

**教训**：在`CheckoutHandler`初期开发时，我一度想直接在Handler里拼接SQL字符串（为了省事），后来克制住了，坚持通过`OrderRepository`操作数据库。事实证明这是正确的——后来修改订单表结构时，只需改Repository，Handler完全不变。

#### （3）设计模式使用了吗？如何用的？

本学期课程的核心要求之一就是设计模式的应用。以下是项目中实际使用的设计模式及具体场景：

| 设计模式 | 使用场景 | 具体实现 |
|----------|----------|----------|
| **策略模式** | UI风格切换 | `UIRenderer`抽象基类，`SimpleRenderer`和`FancyRenderer`是两种具体策略。`ClientController`持有`renderer`指针，运行时调用`setRenderer()`切换。 |
| **策略模式** | 促销算法族 | `IPromotion`接口，`DiscountPromotion`、`CouponPromotion`、`PriceCutPromotion`分别封装打折、满减、降价算法。`PromotionContext`在结算时选择合适的策略。 |
| **装饰模式** | 促销叠加 | `PromotionDecorator`继承自`IPromotion`，内部持有`unique_ptr<IPromotion>`。多个装饰器层层包装，实现“先打9折，再满200减30”的叠加效果。 |
| **观察者模式** | 异步消息队列 | `TaskQueue`是被观察的目标（Subject），`WorkerPool`中的每个`Worker`线程是观察者（Observer）。新任务入队时`notify_one()`唤醒一个等待的Worker。 |
| **工厂模式** | 创建Handler对象 | `HandlerFactory::createHandler(code)`根据协议码返回对应的`ICommandHandler`子类实例，调用者无需知道具体类名。 |
| **命令模式** | 请求封装 | 每个业务请求（展示商品、结算、退货）都封装为独立的`ICommandHandler`子类，`execute()`方法统一执行。 |
| **单例模式** | 任务队列 | `TaskQueue::getInstance()`返回全局唯一实例，保证所有线程共享同一个任务队列。 |
| **RAII（资源获取即初始化）** | Socket/数据库连接管理 | `TcpClient`构造时创建socket，析构时自动`closesocket`；`SQLiteHelper`构造时打开数据库，析构时`sqlite3_close`。异常安全。 |

**关键代码示例——装饰模式的促销链构建**：

```cpp
// 客户端请求的promo_ids = [1, 3] 表示同时选择"9折"和"满200减30"
std::unique_ptr<IPromotion> buildPromotionChain(const std::vector<int>& promoIds,
                                                 PromotionFactory& factory) {
    std::unique_ptr<IPromotion> chain = nullptr;
    for (int id : promoIds) {
        auto promo = factory.create(id);
        if (!promo) continue;
        if (!chain) {
            chain = std::move(promo);
        } else {
            // 用装饰器将新促销包装到链上
            chain = std::make_unique<PromotionDecorator>(std::move(chain), std::move(promo));
        }
    }
    return chain;
}
// 调用：auto chain = buildPromotionChain({1, 3}, factory);
// 效果：先执行满减，再执行9折（装饰器层层嵌套）
```

#### （4）多线程用了吗？如何用的？

**使用场景**：服务端需要同时处理多个客户端连接，且每个请求可能涉及数据库IO，必须使用多线程避免阻塞。

**线程模型设计：**

```
┌─────────────────────────────────────────────────────────────┐
│  服务端线程布局（共1 + N + 4 = 约N+5个线程）              │
├─────────────────────────────────────────────────────────────┤
│  ▶ Acceptor线程（1个）                                     │
│    - 持续accept()新连接                                    │
│    - 每accept一个客户端，启动一个ClientHandler线程         │
│                                                           │
│  ▶ ClientHandler线程（每个客户端1个，动态增减）            │
│    - recv()接收该客户端的请求                             │
│    - 将请求包装为Task，push到TaskQueue                    │
│    - 发送响应（由Worker处理后异步发回）                    │
│                                                           │
│  ▶ WorkerPool线程（固定4个）                              │
│    - 阻塞等待TaskQueue中有新任务                          │
│    - 取出Task，根据协议码调用对应的Handler                │
│    - 执行完毕后，通过clientFd发回响应                     │
│                                                           │
│  ▶ 主线程（阻塞在用户输入，用于stop控制）                 │
└─────────────────────────────────────────────────────────────┘
```

**同步原语使用：**

| 同步原语 | 使用场景 | 具体代码 |
|----------|----------|----------|
| `std::mutex` | 保护TaskQueue的共享队列 | `std::lock_guard<std::mutex> lock(mtx); queue.push(task);` |
| `std::condition_variable` | Worker等待新任务 | `cond.wait(lock, [this](){ return !queue.empty() || shutdown; });` |
| `std::mutex` | 保护库存扣减（防止超卖） | `std::lock_guard<std::mutex> lock(stockMutex); product->stock -= qty;` |
| `std::atomic<bool>` | 控制线程安全关闭 | `std::atomic<bool> running;` 多个线程安全读写 |
| 线程局部存储（隐式） | 每个ClientHandler线程独立管理自己的socket | 局部变量`SOCKET clientFd`，线程栈隔离 |

**生产者-消费者模型核心代码**（已验证无误）：

```cpp
// 生产者（ClientHandler线程）
void TcpServer::clientHandler(SOCKET clientFd) {
    while (running) {
        ProtocolHeader header; std::string body;
        if (!recvFullPacket(clientFd, header, body)) break;
        Task task{clientFd, header.code, body, getCurrentMs()};
        TaskQueue::getInstance().push(task);  // 入队并notify
    }
    closesocket(clientFd);
}

// 消费者（Worker线程）
void WorkerPool::workerLoop() {
    while (running) {
        Task task = TaskQueue::getInstance().pop();  // 阻塞等待
        if (task.protocolCode == 0) continue;
        handleTask(task);  // 执行业务逻辑
    }
}
```

#### （5）描述你认为比较经典的处理技术

**① 基于长度前缀的粘包处理**

TCP是流式传输，没有消息边界。我采用**先读固定长度头部，解析出体长，再循环读满体长**的方式切割消息。这个实现虽然基础，但作为自定义协议的经典做法，值得总结。

```cpp
// 核心技巧：循环recv直到收满指定字节数
bool recvExact(SOCKET fd, char* buf, int len, int timeoutSec) {
    int received = 0;
    while (received < len) {
        int ret = recv(fd, buf + received, len - received, 0);
        if (ret <= 0) return false;  // 连接关闭或错误
        received += ret;
    }
    return true;
}
```

**② RAII管理多资源（异常安全）**

服务端涉及Socket、SQLite连接、动态内存等多资源，使用RAII确保异常时自动释放：

```cpp
class TcpClient {
    SOCKET sockfd;
public:
    TcpClient() : sockfd(socket(...)) {}
    ~TcpClient() { if (sockfd != INVALID_SOCKET) closesocket(sockfd); }
    // 禁止拷贝，允许移动
};

class SQLiteHelper {
    sqlite3* db;
public:
    SQLiteHelper(const std::string& path) { sqlite3_open(path.c_str(), &db); }
    ~SQLiteHelper() { if (db) sqlite3_close(db); }
};
```

**③ 内存锁 + 数据库原子更新 双重保障防超卖**

高并发下，两个线程同时抢最后一个库存。解决方案：
- **内存锁**：`std::mutex`保护`Product`对象的`stock`字段，保证同一时刻只有一个线程进入扣减区域。
- **数据库原子更新**：`UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`，即使内存锁失效，数据库层面也能防止超卖。

**④ 异步消息队列与观察者模式**

这是本系统设计上最亮眼的技术。服务端不直接同步处理请求，而是通过消息队列缓冲，实现：
- **削峰填谷**：突发流量时请求先入队，Worker慢慢消费。
- **解耦**：通信层（生产者）和业务层（消费者）彼此独立，修改业务逻辑不影响通信代码。
- **可扩展**：增加Worker数量即可提升吞吐量。


### 二、本周遇见了哪些技术问题，如何解决的？

本周在联调和集成过程中遇到了几个新问题：

| # | 问题描述 | 原因分析 | 解决方案 |
|---|----------|----------|----------|
| 1 | 服务端启动后bind失败，报"Address already in use" | 上次程序异常退出，端口未被操作系统回收（TIME_WAIT状态） | 在`bind`前设置`SO_REUSEADDR`选项：<br>`int opt = 1; setsockopt(listenFd, SOL_SOCKET, SO_REUSEADDR, (char*)&opt, sizeof(opt));` |
| 2 | 客户端发送请求后，服务端recv返回0，连接被断开 | 客户端发送后立即关闭socket，服务端未来得及处理 | 客户端发送后**不立即关闭**，而是等待接收响应后才关闭。使用`shutdown(SD_SEND)`半关闭，保留接收能力。 |
| 3 | SQLite执行`BEGIN TRANSACTION`后，后续SQL报"cannot start a transaction within a transaction" | 事务嵌套问题：某些SQL操作内部已开启隐式事务 | 在`CheckoutHandler`中统一控制事务边界，确保每个结算请求只开启一次`BEGIN`，最后`COMMIT`或`ROLLBACK`。 |
| 4 | 客户端同时运行接收线程和主线程，`std::cout`输出偶尔乱序 | 两个线程同时往终端打印，缺少同步 | 主线程和接收线程的输出统一通过`UIRenderer`进行，`UIRenderer`内部使用`std::mutex`保护所有`cout`操作。 |
| 5 | 促销链装饰器嵌套后，`getDescription()`显示不完整 | 装饰器只返回了当前层描述，未递归调用下层 | 修正：`ExtraDiscountDecorator::getDescription()`调用`wrapped->getDescription()`并追加自己的描述。 |
| 6 | 结算成功后，订单明细中的`product_name`为空 | 插入`order_items`时未从商品对象获取名称 | 修正：在`CheckoutHandler`中，从`Product`对象复制`name`到`OrderItem`，而非留空。 |

**问题1的解决代码**：

```cpp

if (setsockopt(listenFd, SOL_SOCKET, SO_REUSEADDR, (char*)&opt, sizeof(opt)) == SOCKET_ERROR) {

}
```

#### 3.2 中期架构优化（如有余力或扩展需求）

**① 将同步阻塞Socket替换为事件驱动（IOCP/select）**

当前每客户端一线程的模式，在客户端数量超过100时性能下降明显。可以改为单线程事件循环（`select`/`poll`）或Windows上的**IOCP**（完成端口），用更少的线程处理更多的连接。

```cpp
// 未来方向：使用select管理多个socket
fd_set readSet;
FD_ZERO(&readSet);
FD_SET(listenFd, &readSet);
// 将所有clientFd加入readSet
select(maxFd + 1, &readSet, nullptr, nullptr, nullptr);
// 遍历有活动的socket，统一处理
```

**② 引入连接池管理数据库连接**

当前每个Repository都独立创建数据库连接，在高并发下可能耗尽数据库连接数。可以设计`ConnectionPool`单例，维护一组预创建的连接，Worker使用时借用、用完归还。

**③ 支持多用户会话管理**

当前系统仅支持单用户登录，未维护会话状态。可以增加`SessionManager`，在用户登录后生成`session_token`，后续请求携带token验证身份。

#### 3.3 对个人技术成长的反思

回顾五周来的开发过程，我认为最大的收获不是代码本身，而是**从"会写类"到"会设计系统"** 的跨越：

- **以前**：面向对象 = 把函数放到类里
- **现在**：面向对象 = 识别变化点、封装变化、面向接口编程、依赖注入、合理使用设计模式

比如促销模块的设计，如果采用面向过程的方式，一定是满屏的`if-else`（如果是打折则这样，如果是满减则那样）。但采用策略+装饰模式后，新增一种促销类型只需新增一个类，核心结算代码零修改——这就是**开闭原则**的价值。
